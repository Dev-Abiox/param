## 2026-04-27 — Patient PDF Disclosure Spec, Option A

**Status:** Workflow Recommendations temporarily withheld from patient
PDF pending counsel review of disclosure language per the Patient PDF
Disclosure Specification (April 2026).

**What changed:**

- New per-lab feature flag `Lab.patient_pdf_workflow_recs_enabled`
  (default `False`).  When `False`, the rule-based Workflow
  Recommendations table is suppressed from the patient-facing PDF
  generated by `frontend/src/lib/generateReport.js`.
- Migration `screening/0013_lab_patient_pdf_workflow_recs.py` adds the
  field; every existing lab row defaults to `False` at migration time,
  so every patient PDF generated post-deploy withholds the section
  immediately.
- `ScreeningSerializer.lab_workflow_recs_enabled` and the live
  `/api/screening/predict` response now surface the flag under
  `labWorkflowRecsEnabled` (camelCase, fail-closed default).
- `buildResultFromScreening` propagates the flag tolerantly across
  both casings (`lab_workflow_recs_enabled` from GET, camelCase from
  live predict).
- `generateReport.js` gates the Workflow Recommendations table on
  `result.labWorkflowRecsEnabled === true`.  Any other value — false,
  null, undefined, missing — suppresses the section.

**What did not change:**

- `apps/screening/clinical_rules.py` — untouched.  §A.6 isolation
  contract holds; B12 ML output unchanged (`final_model_lr_yj.pkl`
  not modified).
- `frontend/src/components/ResultPanel.js` — on-screen teal
  Workflow Recommendations cards still render for every screening.
  Clinicians reviewing the case in-platform see the rule output as
  before; only the patient-facing PDF withholds it.
- `clinicalRules` field on the API response — still populated.  Data
  flow is unchanged; the gate is presentation-layer only.

**Why:**

The Patient PDF Disclosure Specification establishes that the patient
is the eventual reader of the PDF.  The rule output as currently
phrased uses clinical jargon ("microcytic + hypochromic", "Mentzer >
13"), raw confidence tiers ("high"/"medium"/"low"), and module names
that name conditions directly ("Iron Deficiency").  None of that is
appropriate for a layperson reader and none has counsel sign-off.

The spec requires three reviewers (PATectual, regulatory consultant,
commercial counsel) to mark which language they sign off verbatim
versus which language they redraft, before any of it goes on a real
patient artefact.  That review has not happened yet, so the section
is suppressed by default until it does.

**How to re-enable per lab (Option B precondition):**

When counsel has signed off on the disclosure language, the lab has
configured a DPO email (DPDP POA P0-2 unblocked), grievance email,
and pathologist sign-off workflow (DSC or wet-signature audited per
the commercial-launch readiness gate), flip the flag for that lab:

```sql
UPDATE labs
SET patient_pdf_workflow_recs_enabled = TRUE
WHERE code = '<LAB-CODE>';
```

No admin UI exposes the flag deliberately — the flip is a manual
operations step tied to a documented readiness audit per lab.

**Tests:**

- `backend_v3/tests/test_patient_pdf_flag.py` — 7 cases: field
  declaration, serializer method, fail-closed on missing lab,
  migration presence, clinical_rules isolation invariant.
- `frontend/src/__tests__/clinicalRules.test.js` — 5 new cases on
  the flag pass-through (explicit true / explicit false / missing /
  camelCase / coercion).
- All previously passing tests still pass: 41 + 12 + 9 backend, 12
  frontend = 77 backend + 25 frontend.

**B12 regression check:**

`apps/screening/ml_engine.py` and the `final_model_lr_yj.pkl`
artefact are bit-identical to pre-Option-A state.  Run-time
prediction for any given CBC produces the same risk class,
probabilities, and indices as before.  The only behavioural change is
PDF rendering.
