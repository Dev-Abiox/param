# User Seamlessness Audit

## Executive summary

Overall grade: **C+**. Core flows work when the happy path is followed, but several deliberate-design gaps will bite real users. Top 3 friction points: (1) the login response exposes a `mfaSetupRequired` flag that the frontend completely ignores — a first-login LAB user gets no routing hint and may hit silent 403s from `IsMFAVerified` before they find Settings; (2) the "Use a backup code instead" button on the MFA challenge screen has no `onClick` handler — it is dead UI even though the backend supports backup codes; (3) the `SetPassword` success screen displays the plaintext password back to the user inside the DOM ("Save these credentials before navigating away"), which is both a confused UX and a leak surface. The billing 402 path, bulk-import UI, and trial-expiry warning email are all missing. On the positive side, consent flow, PHI audit logging, doctor isolation, and MFA EMAIL migration banner are well-executed.

## Scope

- **Personas audited**: SUPER_ADMIN (platform operator), LAB (first-login admin → daily user), DOCTOR (review-only consumer).
- **Flows covered**: org provisioning, credential email, password setup, login + error distinguishability, MFA setup + challenge, onboarding wizard, screening predict + detail drawer, work queue triage, doctor review + isolation, billing upgrade (Razorpay), quota 402, empty states.
- **Out of scope**: security review (separate), code quality, perf benchmarking, accessibility, mobile UX, webhook consumer UX, FHIR bundle consumers, and the super-admin delete-org confirmation UX (beyond the scope of first-use journeys).

## Findings by persona

### SUPER_ADMIN

- 🟠 **Friction — Create-Org is a single-shot submit with no progress feedback for the 5-15 s tenant creation.** [PlatformCreateOrg.js:202-208](../../frontend/src/views/platform/PlatformCreateOrg.js#L202) just toggles `{loading ? "Creating…" : "Create Lab & Send Credentials"}`. The backend [platform_views.py:290-354](../../backend_v3/apps/core/platform_views.py#L290) does a synchronous `transaction.atomic` that creates Organization, Domain, User, TenantSubscription, then opens a `schema_context` to create the Lab — all in the request path. On a cold DB this is reliably 3-10 s. The user sees a dead spinner with no "creating tenant schema…" sub-text.
- 🟠 **Friction — No email bounce / delivery confirmation surface.** [PlatformCreateOrg.js:64-66](../../frontend/src/views/platform/PlatformCreateOrg.js#L64) says "Login credentials have been sent to X" — but the platform admin has no way to see *whether* the email actually delivered. [tasks.py:988-1010](../../backend_v3/apps/billing/tasks.py#L988) swallows `send_mail` failures into a retry loop and only logs `billing.lab_created_email_failed`. A resend endpoint exists ([platform_views.py:759-799](../../backend_v3/apps/core/platform_views.py#L759)) but nothing in the frontend UI surfaces it on the org detail page.
- 🟢 **Works well** — Plan selection cards are clean, plan limits are formatted in Indian numerals, and the success screen has both "View Lab" and "All Labs" CTAs.

### LAB

- 🔴 **Blocker — `mfaSetupRequired` from login response is never handled.** [LoginView:232-245](../../backend_v3/apps/core/views.py#L232) returns `{access_token, mfaSetupRequired: True, ...}` for LAB users without MFA configured. The frontend login handler at [App.js:103-138](../../frontend/src/App.js#L103) treats this as a normal login: it calls `getMe`, sets the user, then `checkOnboardingRedirect` navigates to `/onboarding`. But the Onboarding view tries to call `AdminService.createLab` and `BillingService.getOnboardingStatus`, both of which require `IsMFAVerified` and will silently 403 in the catch blocks (e.g. [Onboarding.js:82-84](../../frontend/src/views/Onboarding.js#L82) silently ignores 403s). The user sees Onboarding step 1 render, submits, then gets `err.response?.data?.error` (usually "MFA setup required…" from [permissions.py:155](../../backend_v3/apps/core/permissions.py#L155)). Nothing routes them to `/settings` where MFASetup lives.
- 🔴 **Blocker — "Use a backup code instead" is dead UI.** [Login.js:211-218](../../frontend/src/views/Login.js#L211) renders the button with `data-testid="use-backup-code-button"` but no `onClick` handler. A real user who has lost their authenticator (or their phone is in another room) will click it and *nothing happens*. Backend supports backup-code verification via [mfa.py:159-164](../../backend_v3/apps/core/mfa.py#L159) — the frontend just never wired it up.
- 🟠 **Friction — `SetPassword` success screen shows the plaintext password.** [SetPassword.js:71-74](../../frontend/src/views/SetPassword.js#L71) renders `<span>{password}</span>` with the label "Password" after successful set. The user just typed it; showing it back provides no value, leaks to any shoulder-surfer, and persists in the DOM until navigation. Remove the password line — username is enough.
- 🟠 **Friction — Password-setup link is 3 days; after that the user is stranded.** [tasks.py:448-461](../../backend_v3/apps/billing/tasks.py#L448) uses Django's `default_token_generator` which honours `PASSWORD_RESET_TIMEOUT` (default 3 days, not 25 hours as the email claims… wait, the email does say 3 days — [tasks.py:981](../../backend_v3/apps/billing/tasks.py#L981) — so that matches). But: if the token is expired and the user clicks through, [SetPassword.js:36-38](../../frontend/src/views/SetPassword.js#L36) shows a generic "Failed to set password. The link may have expired." with no CTA to request a new one. The user has to email support or find the platform admin.
- 🟠 **Friction — Onboarding step 1 cannot be skipped.** [Onboarding.js:310-311](../../frontend/src/views/Onboarding.js#L310) says "A lab is required to start screening" instead of offering Skip. Meanwhile the backend `PlatformCreateOrgView` *already auto-creates a Lab* during provisioning ([platform_views.py:337-354](../../backend_v3/apps/core/platform_views.py#L337)) and sets `onboarding_status.lab_added = True`. So the wizard's resume logic at [Onboarding.js:71-85](../../frontend/src/views/Onboarding.js#L71) should skip directly to step 2 — which it *does*, but the "first visit catch" block ([Onboarding.js:82-84](../../frontend/src/views/Onboarding.js#L82)) silently swallows errors, so if the getOnboardingStatus call 403s (MFA), the user ends up on step 1 and must manually re-enter a lab that already exists → `create lab` will then hit the uniqueness constraint.
- 🟠 **Friction — Login error messages don't distinguish bad-credentials from deactivated-account from rate-limit.** [views.py:173-193](../../backend_v3/apps/core/views.py#L173) returns distinct messages (`'Invalid credentials'` vs `'Account is disabled'` vs `'Organization account is disabled'`), but the frontend [App.js:131-134](../../frontend/src/App.js#L131) only surfaces `err?.response?.data?.error` with the fallback "Invalid credentials. Please check your username/email and password." Since all three backend messages are already in `error`, the fallback only fires when the response has no body. That's fine — BUT the rate-limited case (429 from [LoginRateThrottle](../../backend_v3/apps/core/throttling.py)) returns a DRF `throttled` response with `detail` not `error`, so the user gets the generic "Invalid credentials" message. Confusing for a user who typed correctly 5 times.
- 🟠 **Friction — No visible bulk-import UI.** [screening/views.py:938](../../backend_v3/apps/screening/views.py#L938) exposes `BulkImportView` accepting a CSV; the frontend only has `LisService` wrappers in [api.js](../../frontend/src/services/api.js) — grep confirms no view component. LAB users who were sold on the bulk-import feature have no button to click.
- 🟠 **Friction — 402 "Monthly limit reached" surfaces as a screening-form error, not a dashboard banner.** [PlanLimitMiddleware:255-258](../../backend_v3/apps/billing/middleware.py#L255) returns `{'error': 'Monthly screening limit reached. Please upgrade your plan.'}` with status 402. The frontend [UserWorkspace.js:148-164](../../frontend/src/views/UserWorkspace.js#L148) reads `errData.error` and sets `screeningError` — so the user sees the message inline. But there's no 402-specific handling (grep for `status === 402` across the frontend returns zero hits): no "upgrade now" button, no redirect to `/billing`, no persistent banner. Users hit this *every* subsequent predict attempt until they figure out the upgrade flow.
- 🟠 **Friction — No trial-expiry warning email is sent.** Celery task list has `expire_trials` ([tasks.py:51-90](../../backend_v3/apps/billing/tasks.py#L51)) which transitions TRIAL → EXPIRED at the trial_end but does not email anyone. Grep for `trial_warn|trial_reminder|days_until_expiry` is empty. The only signal is the in-app banner at [AdminBilling.js:279-291](../../frontend/src/views/admin/AdminBilling.js#L279) — users who don't log in won't know the trial is ending.
- 🟢 **Works well** — MFA migration banner ([Login.js:132-137](../../frontend/src/views/Login.js#L132)) explains the TOTP→EMAIL switch clearly. Usage threshold alerts at 80/90/100% are well-targeted ([tasks.py:313-329](../../backend_v3/apps/billing/tasks.py#L313)). Trial / days-remaining chips on the Billing page are prominent.

### DOCTOR

- 🟠 **Friction — Doctors cannot access `/api/screening/queue`.** [screening/views.py:715-716](../../backend_v3/apps/screening/views.py#L715) hard-codes `required_roles = [Role.LAB]`. If a DOCTOR hits `/workqueue`, they get 403. The frontend [WorkQueue.js:262](../../frontend/src/views/WorkQueue.js#L262) passes `userRole={Role.LAB}` unconditionally — suggesting this view was never meant for doctors, but nothing in the routing prevents a doctor from navigating there. Should either be role-gated client-side or backend should let doctors see their own queue.
- 🟠 **Friction — Review has no optimistic-concurrency guard.** [ReviewScreeningView.patch](../../backend_v3/apps/screening/views.py#L834) reads the screening, mutates, and saves — no `If-Match`/`version` check. Two doctors opening the same case in parallel will both write `is_reviewed=True` with their own `clinical_note`; last writer wins and the first doctor's note is silently lost. The drawer ([ScreeningDetailDrawer.js:81-98](../../frontend/src/components/ScreeningDetailDrawer.js#L81)) has no stale-data warning either.
- 🟢 **Works well** — Doctor isolation is correctly enforced at [analytics/views.py:264-275](../../backend_v3/apps/analytics/views.py#L264) and [screening/views.py:841-844](../../backend_v3/apps/screening/views.py#L841) / [893-895](../../backend_v3/apps/screening/views.py#L893) / [696](../../backend_v3/apps/screening/views.py#L696). A doctor filtering by `doctorId=<someone_else>` gets a 403 with a clear message. High-risk WebSocket alerts on the dashboard are a nice touch.

## Cross-cutting findings

- 🟠 **Silent load failures.** [DoctorDashboard.js:17-25](../../frontend/src/views/DoctorDashboard.js#L17), [LabList.js:16](../../frontend/src/views/LabList.js#L16), [DoctorList.js:16](../../frontend/src/views/DoctorList.js#L16), [PatientRecords.js:37](../../frontend/src/views/PatientRecords.js#L37), [WorkQueue.js:52-54](../../frontend/src/views/WorkQueue.js#L52) all `console.error` the failure and fall back to empty state with no user-visible error. For a lab manager who just lost Wi-Fi, "No recent screenings found" is misleading — they'll assume data was wiped.
- 🟠 **ML-not-ready 503 is shown as a generic screening error.** [PredictView._run_prediction:203-207](../../backend_v3/apps/screening/views.py#L203) returns a 503 with `'ML screening service unavailable. Models not loaded.'`. The frontend surfaces this verbatim in a red banner with no retry button, no ETA, no "contact support" CTA. For a lab running a busy morning queue, this is a full stop.
- 🟠 **No progress indicator for bulk import on backend.** [BulkImportStatusView:1038-1062](../../backend_v3/apps/screening/views.py#L1038) returns `processedRows/totalRows/failedRows` — good. But since there's no frontend UI (see LAB finding above), users can't see progress. If/when the UI is added, the API is ready.
- 🟢 **Consent flow UX is solid.** [UserWorkspace.js:125-130](../../frontend/src/views/UserWorkspace.js#L125) auto-runs screening after consent capture, and the modal backdrop + close button work as expected. Consent-expired returns a 422 with a `code: "consent_expired"` that the frontend *could* use to render a "Renew consent" CTA (currently just shows the generic error).
- 🟢 **WebSocket "Live" indicator** in the work queue ([WorkQueue.js:121-126](../../frontend/src/views/WorkQueue.js#L121)) is a nice reassurance signal.

## Prioritized fix list

1. [App.js:109-112](../../frontend/src/App.js#L109) — handle `result.mfaSetupRequired`: navigate to `/settings?tab=mfa` and show a banner "You must set up MFA before continuing." — ~1 h — **High impact** (every first-login LAB user hits this).
2. [Login.js:211-218](../../frontend/src/views/Login.js#L211) — wire up the backup-code button to a new `/mfa/verify-backup-code` flow or at minimum hide the button until implemented — ~2 h — **High impact** (feature advertised, doesn't work).
3. [SetPassword.js:71-75](../../frontend/src/views/SetPassword.js#L71) — remove the plaintext password display; keep username only — ~10 min — **High impact** (leak surface + confusion).
4. [UserWorkspace.js:148-164](../../frontend/src/views/UserWorkspace.js#L148) — branch on `err.response?.status === 402` to render a dedicated "You're out of quota — upgrade now" modal with a button to `/billing` — ~1 h — **High impact**.
5. Add a frontend **BulkImport.jsx** view that hits `POST /api/screening/bulk-import` and polls `BulkImportStatusView` — ~1 day — **Medium impact** (feature sold but invisible).
6. Add a Celery beat task `send_trial_expiring_warning` scheduled at trial_end − 3 days — ~3 h — **Medium impact**.
7. [ReviewScreeningView](../../backend_v3/apps/screening/views.py#L824) — add `If-Match: <updated_at>` optimistic-concurrency check; return 409 when stale — ~2 h — **Medium impact** (silent lost notes under concurrency).
8. [DoctorDashboard.js](../../frontend/src/views/DoctorDashboard.js), [PatientRecords.js](../../frontend/src/views/PatientRecords.js), [LabList.js](../../frontend/src/views/LabList.js) — surface a toast or inline banner for load failures instead of silent empty state — ~2 h total — **Medium impact**.
9. [SetPassword.js:36-38](../../frontend/src/views/SetPassword.js#L36) — when the token is expired, show a "Request new link" button that hits `POST /api/auth/forgot-password` — ~30 min — **Medium impact**.
10. [PlatformCreateOrg.js:202-208](../../frontend/src/views/platform/PlatformCreateOrg.js#L202) — swap synchronous create for a 202 + job-status polling, OR show a step-by-step progress ("Creating schema… Creating admin user… Sending email…") — ~half day — **Low impact** (super-admins only).
11. [PlatformOrgDetail.js](../../frontend/src/views/platform/PlatformOrgDetail.js) — surface the existing `PlatformResendCredentialsView` ([platform_views.py:759](../../backend_v3/apps/core/platform_views.py#L759)) as a "Resend credentials" button per-user — ~1 h — **Low impact**.
12. [Onboarding.js:82-84](../../frontend/src/views/Onboarding.js#L82) — don't silently swallow `getOnboardingStatus` errors; if the error is 403 (MFA required), redirect to `/settings`; otherwise surface a banner — ~30 min — **Medium impact** (fallback to step 1 when tenant already has a lab is user-confusing).
13. [WorkQueue.js](../../frontend/src/views/WorkQueue.js) — role-gate client-side so DOCTOR never navigates here, or broaden backend `required_roles` to include DOCTOR with per-doctor filtering — ~2 h — **Low impact**.

## Tested vs untested

- **Tested by tracing code**: login → MFA challenge → verify; super-admin create-org transaction + email trigger; predict → persist → side-effects; doctor isolation on review/explain/consent/cases endpoints; 402 PlanLimitMiddleware trigger; SetPassword happy path; Onboarding resume; MFA setup state machine.
- **Not verified (would need live environment)**: Razorpay webhook delay race (did payment actually upgrade the plan before the user refreshes?), real email delivery + bounce handling, actual ML-predict latency, WebSocket reconnect after network blip, CSV bulk import under partial failures (backend exists but no frontend consumer to trace end-to-end), browser back-button behaviour mid-onboarding, MFA OTP race when user resends twice in 60 s.
